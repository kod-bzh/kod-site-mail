# Autoriser la collecte Google Postmaster

Cette procédure opérateur conserve les inscriptions existantes. Elle ne crée ni inscription Postmaster, ni boîte, ni modification DNS. Une inscription validée et une autorisation API sont deux vérifications distinctes.

1. Confirmer dans Postmaster les droits du compte sur les domaines demandés. Activer l’API officielle Postmaster dans le projet Google du client OAuth serveur. Le client doit accepter l’URI HTTPS de retour `/api/migration/oauth/google/callback` de `AUTH_URL` ; ce chemin reste compatible avec les migrations existantes.
2. Appeler, côté serveur avec le jeton administrateur plateforme, `POST /api/v1/mail/connectors/google/oauth?organizationSlug=...`, corps `{"domains":["mail.d2-group.fr","d2-group.fr"]}`. Les clés d’organisation, y compris `deliverability:read`, ne peuvent pas démarrer une autorisation.
3. Ouvrir `authorizationUrl` dans le navigateur de l’opérateur propriétaire. Ce lien est une capacité temporaire à protéger, valable quinze minutes. Ne pas le publier, ni copier les paramètres de callback dans des journaux. Confirmer uniquement le droit `https://www.googleapis.com/auth/postmaster.readonly` affiché par Google. Aucun droit Gmail, contacts, agenda ou envoi n’est demandé.
4. Le retour JSON `authorized` confirme la vérification des droits Google et le stockage chiffré de l’autorisation hors ligne. Il ne confirme pas l’existence de statistiques. Vérifier ensuite `/mail/connectors` et `/mail/domains/{domain}/reputation` : la première collecte peut rester `insufficient_data`, notamment à faible volume Gmail personnel.

Les variables serveur `GOOGLE_POSTMASTER_CLIENT_ID` et `GOOGLE_POSTMASTER_CLIENT_SECRET` forment une paire facultative dédiée. Si elles sont toutes deux absentes, le client OAuth serveur des migrations est réutilisé avec le seul scope Postmaster ; ses autres grants ne sont pas importés. Une paire dédiée incomplète est refusée. Google peut refuser le scope si le projet n’est pas configuré, exiger une validation de l’application ou limiter les utilisateurs d’un projet en test. Ne pas contourner ces contrôles.

Protection : état aléatoire 256 bits stocké sous forme de hash, PKCE S256, cookie navigateur HttpOnly/Secure/SameSite=Lax, état consommé une seule fois sous verrou, vérification de la propriété KOD avant et après l’échange, verrou sur les domaines avant conservation du grant. Les domaines d’autres organisations sont refusés. Les réponses fournisseur sont bornées et aucun payload d’erreur, code ou jeton n’est journalisé. L’échange exige explicitement un refresh token et le seul scope demandé ; un résultat plus large ou incomplet est refusé, sans remplacer l’accès actif. Les réponses API sont `no-store` et `no-referrer`.

Le vérificateur PKCE est chiffré dans les réglages internes du connecteur jusqu’au callback ou au prochain démarrage ; au-delà de quinze minutes il devient inutilisable même s’il reste stocké. Les jetons sont chiffrés côté serveur, exclus des réponses et conservés tant que le connecteur est configuré. L’expiration n’est renseignée que si Google la fournit. Les refus ultérieurs de refresh déclenchent `authorization_required` ; renouveler le consentement après révocation ou expiration. Aucune garantie d’arrivée hors spam ou de lecture ne découle de cet accès.

Documentation officielle : [OAuth serveur Google](https://developers.google.com/identity/protocols/oauth2/web-server), [domaines et droits Postmaster](https://developers.google.com/workspace/gmail/postmaster/reference/rest/v1/domains).
